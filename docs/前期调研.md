# 星槎 Xīngchá · 产品前期调研

> **星槎**（xīng chá）——《博物志》载有人乘槎溯河，直抵天河；明代费信随郑和下西洋，著《星槎胜览》。
> 一条渡海之筏：把提示词渡成可被调用的服务。

| 项 | 内容 |
|---|---|
| 文档版本 | **v1.0 终版**（2026-08-28） |
| 文档性质 | 立项前调研。结论均标注验证方式；被推翻的假设保留原处，不做美化 |
| 调研方法 | 实机 probe（Python 3.13.14 + pydantic-ai 2.35.3）· 官方文档核对 · 公开 API 实测 · 竞品部署事实核查 |
| 相对前版 | v0.3 一处核心卖点被实测推翻；v1.0 补齐竞品能力矩阵、官方路线判断与需求信号取证。见[修订记录](#修订记录) |

---

## 摘要

星槎是一个**自部署的 Agent 控制面**：管理员在 Web 表单里把提示词配置成 Agent，调用方用 OpenAI 兼容 API 访问，系统按用户计量用量、强制配额，并支持把 Agent 定义导出带走。技术上它是 pydantic-ai 官方 `AgentSpec` 的一层薄运营外壳。

**核心技术发现（实测）。**pydantic-ai 在 **Python 路径**（真 Pydantic model 作 `output_type`）下完整校验输出并触发重试；但在 **YAML 声明式路径**（`AgentSpec.output_schema` → `StructuredDict`）下**完全不校验**——同一份违规数据，前者拦截、后者放行。这不是框架缺陷，是声明式路径丢失了命令式路径已有的保证。**星槎的技术价值由此获得精确表述：在声明式路径上恢复这份保证。**

**竞争格局已探明，四家各缺一角。**`pydantic-ai-server`（26★）是纯 Python 定义、无发现无鉴权无计量；`croit/llm-gateway`（16★）运维能力极强但**无 agent 概念**；`Cognipeer/console`（23★）多租户完备但非 pydantic-ai 系；官方 `to_openai_responses()` 只服务**单个** agent。星槎唯一独占的组合是：**声明式 Web 表单 + AgentSpec 可移植 + Agent 进入客户端模型选择器 + pydantic-ai 原生**。

**但"硬配额"不再是差异点**——croit 的配额维度（请求/token/花费 × 时/日/周/月 × 全局/角色/用户）比星槎原规划更强。

**需求信号取证结果为弱。**pydantic-ai 社区点赞最高的诉求全是框架能力（结构化输出 74👍、Graphs、Skills），无一条要求部署/网关/多租户；官方那个服务化 PR 获得 0 反应；三个同形态项目合计不到 70 star。

**文献调研规模**：arXiv 系统检索 18 个主题簇 / 66 条检索式，去重语料 **2005 篇**，标题级强命中 **552 篇**（75% 为 2025 年后）。**最重要的发现是一处自我修正**：约束解码并非零成本的最强保证——五条独立证据显示它存在「对齐税」，会扭曲概率分布、偏向合法但次优的输出，在工具调用弃权场景最差达 −29.5 分。因此星槎的价值不是替用户选最强档，而是**把四档权衡摆出来并标注代价**。另有两项新采纳：schema 字段措辞会显著影响准确率（可做成表单 lint，成本极低）、直接采用现成的 SOB 基准而非自建。**演进方向收敛为四条**，全部围绕"输出保证"这一主线：分级输出保证（实测 OpenRouter 目录中 **23% 的模型不支持原生 structured outputs**，星槎按能力自动分级并向用户显式标注）· 推理与格式两阶段（EMNLP 2024 已证实格式约束会损害推理）· 校验驱动的模型升级（FrugalGPT 思想的窄化版，复用现成的确定性质量信号）。通用路由、语义缓存、自动提示词优化等五个方向**主动拒绝，且拒绝理由均有文献支撑**（见 [12.8](#128-明确拒绝的方向含文献依据)）——其中一条负面发现值得记：学界的多租户 LLM 服务研究几乎全是 GPU 侧调度，与星槎需要的 API 网关级配额是两个问题，得不到助力。

**结论**：作为自用工具价值确凿；作为开源项目是一个**技术定位清晰、但需求尚未被证明**的窄切口。按窄 Alpha 验证推进，不按商业产品立项。

# 第一部分 · 为什么做

---

## 1 问题定义

*本章回答：谁在什么场景下卡住了，现有方案为什么不够。*

### 1.1 触发场景

把一段调好的提示词变成"团队能用的东西"，今天只有三条路，每条都有明确代价：

| 路径 | 解决了什么 | 代价 |
|---|---|---|
| 每人一份 key，各自复制提示词 | 起步成本零 | 提示词漂移到各处 · key 无法回收 · 钱花在哪不知道 |
| 上模型网关（New API / LiteLLM） | key 收归一处 · 额度可控 · 用量可见 | 它只认**模型**；提示词依然散落在每个人的客户端里 |
| 上 Agent 平台（Dify / Langflow） | 提示词成为受管资产 | 8 容器常驻 · api+worker 即占 1.3GB · 平台锁定 · 结构化输出不可靠 |

**星槎针对的区间**：第一条想升级、第二条不够用、第三条太重。

### 1.2 目标用户

| | 画像 | 核心诉求 |
|---|---|---|
| **P1** | 小团队技术负责人（3–15 人） | 给同事一批开箱即用的 Agent，不必每人配 key；要能看见钱花在谁身上，并能真正卡住超支 |
| **P2** | 独立开发者 | 把提示词资产沉淀成服务，业务代码用 OpenAI SDK 直接调，不想为此养 8 个容器 |
| **P3** | 教研 / 企业内部工具 | 用量可见 · 费用可控 · **控制面自持**（配置、日志、用量、密钥留在自己机器上）· 部署可审计 |

> **P3 的边界必须说清楚**：默认走 OpenRouter 时，提示词、用户输入、上传文件仍会发送给 OpenRouter 及其背后的模型提供商。星槎自部署的是**控制面**，不是数据面。**不可宣传「数据不出境」**——只有把 `OPENROUTER_BASE_URL` 指向内网模型服务时，该表述才成立。

### 1.3 典型场景

1. **结构化抽取** —— 工单、简历、合同文本抽成固定字段直接入库。要求输出形状可信，不能"这次多一个字段下次少一个"。
2. **内部文档问答** —— 多轮对话 + 联网检索，给非技术同事使用。
3. **批量内容处理** —— 业务代码里把 Agent 当函数调用，需要稳定的类型契约。
4. **给非技术同事一个能用的 AI 工具** —— 他们在 Cherry Studio 的下拉框里选一个 Agent，不需要知道背后是什么模型、什么提示词。

> 场景 1–3 全部依赖「结构化输出可靠」，这决定了它在 [5.3](#53-卖点乙在声明式路径上恢复输出校验) 中的权重。

## 2 产品定义

*本章回答：它是什么、不是什么，哪些约束不可妥协。*

### 2.1 定位

**给已经选择（或愿意选择）Pydantic AI 的小团队：一条最短的 Agent 发布、分发、计量、退出路径。**

展开为四件事：把提示词配置成 Agent（Web 表单）· 分发给人用（OpenAI 兼容 API + 令牌）· 看住花销（计量 + 配额）· 随时能走（AgentSpec 导出）。

v0.3 曾把定位写成「两条成熟赛道之间的空当」。**该说法已被证伪**——交集有人，且不止一家：

```
                    模型粒度                      Agent 粒度
                ┌────────────────────────┬──────────────────────────────┐
  重部署        │  Portkey               │  Dify（8容器/1.3GB）          │
  多中间件      │  LiteLLM + Postgres    │  Langflow / Flowise          │
                ├────────────────────────┼──────────────────────────────┤
  轻部署        │  New API / one-api     │  ★星槎★  pydantic-ai-server  │
  零中间件      │  croit/llm-gateway     │          Cognipeer/console   │
                │  （运维强，无 agent）   │                              │
                └────────────────────────┴──────────────────────────────┘
                                              ↑ 三家先行者，合计不到 70★
```

**格子里没有赢家，不等于格子里有需求。**这是 [R4](#9-风险) 的直接证据，见 [6.4](#64-需求信号取证) 的完整取证。

### 2.2 产品原则（硬约束）

否决性约束——任何与之冲突的功能提案直接驳回，而非权衡。

| ID | 约束 | 含义 |
|---|---|---|
| **C1** | 零三方中间件 | 不依赖 Postgres、Redis、消息队列、向量库、Node 构建链 |
| **C2** | 单进程可跑 | 1C1G 机器足够；单个 asyncio 事件循环，无 worker 池 |
| **C3** | 三条命令上手 | `install` → `serve` → 打开浏览器，中间不插入任何配置文件编辑 |
| **C4** | 简单优先 | 任何让"第一次使用"变复杂的功能，降级为可选或折叠进高级区 |
| **C5** | 复杂场景不封死 | 常用复杂能力给预设模板，极端场景给逃生舱 |
| **C6** | 零锁定 | 任何时刻用户都能带着 Agent 定义离开，且离开后定义仍可运行 |

### 2.3 非目标

明确不做，写入文档以防日后功能蔓延：

| 不做 | 原因 |
|---|---|
| 可视化 DAG 编排 | 拖拽画布是 Dify / Langflow / n8n 的战场，正面竞争必输，且违反 C1 与 C4 |
| 内建向量库与 RAG | 通过 MCP 或外部服务接入，不自建检索栈 |
| 成为模型网关 | 该赛道已挤满（OpenRouter、LiteLLM、New API、Portkey、Vercel AI Gateway、Pydantic 官方 Gateway）。星槎**调用**网关，不做网关 |
| 支付与结算 | 只做用量计量与费用**预估**，不碰收款 |
| 模型微调与托管 | 不在能力范围 |
| K8s Operator / 水平扩展 | 单机定位；需横向扩展的场景不是目标客户 |
| 通用工作流自动化 | 那是 n8n |

## 3 产品形态

*本章回答：管理员和调用方分别看到什么、做什么。*

### 3.1 首次使用的十分钟

C3 的具体兑现路径。全程不需要编辑任何配置文件。

```bash
uv tool install xingcha
xingcha serve
```

启动后终端打印本地地址与一次性 setup token，浏览器中完成五步：

| 步 | 操作 | 产出 |
|---|---|---|
| 1 | 设置管理员密码 | 管理员账号 |
| 2 | 粘贴 OpenRouter Key，可选填中转 base_url，点「测试连接」 | 拉回可用模型列表并缓存 |
| 3 | 从模板新建 Agent → 选「结构化抽取」→ 改提示词 → 右侧 Playground 试跑 → 保存 | 第一个 Agent，已有 slug |
| 4 | 新建用户 + 签发令牌 | `sk-xc-...`（**仅此一次可见**） |
| 5 | 业务代码 `base_url` 指过来，`model` 填 Agent 的 slug | 打通 |

### 3.2 管理员视角：Agent 配置面

表单字段与 `AgentSpec` 一对一映射，不做私有扩展——这是零锁定（[5.2](#52-卖点甲低锁定可退出)）在产品层面的落地形式。

| 分区 | 字段 | 映射到 | 备注 |
|---|---|---|---|
| 基本 | 名称 / 标识 slug / 说明 | `name` / *星槎自有* / `description` | **slug 就是对外的 model id** |
| 提示词 | 指令（大文本框，支持 `{{变量}}`） | `instructions` | 支持从文件载入，便于版本管理 |
| 模型 | 模型选择器（下拉，来自步骤 2 拉回的列表） | `model` | 形如 `openrouter:openai/gpt-5` |
| 输出 | 纯文本 / 结构化（可视字段编辑器，或直接粘 JSON Schema） | `output_schema` | 留空即纯文本 |
| 能力 | 勾选：联网搜索、网页抓取、深度思考、图像生成、MCP、工具搜索…… | `capabilities` | **运行时从 `CAPABILITY_TYPES` 读取**，官方新增能力自动出现 |
| 工具 | 自定义工具（下拉选服务器已注册符号） | 经 `MCP` 能力声明 | 见 [3.6](#36-逃生舱) |
| 高级 | 温度 / max_tokens / 重试 / 工具超时 / 结束策略 | `model_settings` `retries` `tool_timeout` `end_strategy` | 默认折叠（C4） |
| 会话 | 是否启用服务端多轮、历史窗口大小 | *星槎自有* | 见 [3.3](#33-调用方视角三种接入方式) |

**版本化机制**：每次保存产生新版本并记录变更说明。Agent 实例按 `(agent_id, version)` 缓存，编辑后旧实例自然淘汰；回滚即切换 `current_version_id`。

### 3.3 调用方视角：三种接入方式

**方式一 · 现成客户端零改造。** 这是 `GET /v1/models` 的价值所在——Cherry Studio、Open WebUI、Continue、Cursor 及任何 OpenAI SDK 客户端，填入 base_url 与令牌后，**Agent 直接出现在模型下拉框里**，无需任何适配代码。

**方式二 · 业务代码。**

```python
from openai import OpenAI

client = OpenAI(base_url="https://xc.example.com/v1", api_key="sk-xc-...")
r = client.chat.completions.create(
    model="extract",                      # Agent 的 slug
    messages=[{"role": "user", "content": article_text}],
)
# 结构化 Agent：content 是符合 output_schema 的 JSON
```

接口契约要点：

| 项 | 约定 |
|---|---|
| `GET /v1/models` | 每个启用的 Agent 一条，`id` = slug |
| `POST /v1/chat/completions` | `model` = slug；`messages` 支持字符串与 content parts（text / image_url / input_audio / file） |
| 多轮 | 默认无状态，客户端携带完整历史（OpenAI 语义）；可选传 `session_id` 走服务端会话 |
| 流式 | 纯文本 Agent 支持；**结构化输出 Agent 明确返回 400**（见 [8.3](#83-决策-3--结构化输出的-agent-拒绝-streamtrue)） |
| 用量 | `usage` 填真实 token；扩展字段附预估费用 |
| 错误 | 统一 OpenAI 风格 `{"error": {"message", "type", "code"}}` |

**方式三 · 导出脱离星槎。** 见 [5.2](#52-卖点甲低锁定可退出)。

### 3.4 预设模板

C5 的兑现方式：常用复杂场景不靠用户自己摸索，一键填充表单。

| 模板 | 覆盖能力 |
|---|---|
| 纯文本问答 | 最小可用，只有提示词 |
| 多轮对话助手 | 服务端会话 + 历史窗口裁剪 |
| 结构化抽取 | `output_schema` 预填 + `retries=3` |
| 多模态读图 | 预选视觉模型，说明如何传 `image_url` |
| 联网检索 | `WebSearch` + `WebFetch` |
| 深度思考 | `Thinking`，思考预算调高 |
| MCP 工具接入 | `MCP`，填服务器地址 |
| 自定义 Python 工具 | 演示逃生舱引用方式 |

### 3.5 用量与费用

| 视图 | 内容 |
|---|---|
| 管理员 | 全局总览 + 按用户 / 按 Agent / 按模型下钻，可选时间窗 |
| 普通用户 | 仅本人用量 |
| 单次调用明细 | 模型 · token 明细（含缓存读写与音频维度）· 预估费用 · 延迟 · 状态 · 错误码 |
| 配额 | 三级主体（user / token / agent）× 三种窗口（day / month / total），可限金额或次数；超限返回 429 及明确 error type |

**费用一律标注「预估」**并记录 `cost_source`。预估与 OpenRouter 实际账单存在偏差（平台抽成、缓存计价、汇率），产品内提供对账入口，账单以上游官网为准。

> 这不是免责声明，而是防止 [R6](#9-风险) 演变成信任危机的产品设计。

### 3.6 逃生舱

勾选框和模板都不够用时的出口，同时受 C6（零锁定）与安全边界双重约束。

**形态** —— Agent 配置面的「工具」分区提供下拉，列出服务器上已注册的 Python 符号（形如 `python:pkg.mod:symbol`），由 `xingcha ext scan` 发现。

**安全边界** —— Web 表单**绝不接受用户提交的 Python 代码**。理由：

- 在管理后台执行任意 Python 等于把它变成 RCE 入口，管理员令牌一泄露服务器即沦陷；
- 代码字符串存进 SQLite 无法审计，也无法版本管理。

因此代码放在服务器上可 import 的位置，Web 只做**符号选择**：部署即审计，git 即版本管理。

**承载方式** —— 见 [8.1](#81-决策-1--逃生舱默认走-mcp而非进程内代码引用)。

## 4 数据模型

*本章回答：SQLite 单文件里放什么。*

| 表 | 关键字段 | 说明 |
|---|---|---|
| `setting` | key · value_encrypted | OpenRouter key、中转 base_url、Langfuse 配置。敏感值 Fernet 加密 |
| `user` | username · password_hash · role(admin/user) · is_active | 密码 argon2 / bcrypt |
| `token` | user_id · prefix · hash · expires_at · last_used_at | **只存 hash 与前缀**，明文仅创建时展示一次 |
| `agent` | slug · name · is_active · current_version_id | slug 即对外 model id |
| `agent_version` | agent_id · version · **spec_json** · changelog | `spec_json` 即 `AgentSpec` dict（见 [8.2](#82-决策-2--agent-定义整块存-json不拆列)） |
| `run` | agent_id · agent_version · user_id · token_id · session_id · status · latency_ms · error_code | 一次调用一条 |
| `run_usage` | run_id · model · input/output/cache_read/cache_write/audio tokens · requests · tool_calls · cost_usd · cost_source | 字段对齐 `RunUsage` |
| `session` / `session_message` | agent_id · user_id · seq · role · content_json | 服务端多轮；消息用 `ModelMessagesTypeAdapter` 序列化 |
| `quota` | subject_type(user/token/agent) · subject_id · window(day/month/total) · limit_usd · limit_requests | 三级 × 三窗口 |
| `extension` | ref · kind · description | `xingcha ext scan` 发现的可引用符号 |

**索引**：`run(user_id, started_at)` · `run(agent_id, started_at)` · `run_usage(run_id)`

## 5 核心卖点

*本章回答：哪些优势真的构成护城河，哪些只是执行质量，哪些是错的。*

### 5.1 判据

判据统一且唯一：

> **一个熟练工程师照着这份文档，一个周末能不能抄走？**

抄得走的是执行质量，抄不走的才是护城河。**v0.4 追加一条**：卖点必须能被实测证明，未经验证的宣称一律降级为待验证假设。

### 5.2 卖点甲：低锁定，可退出

> v0.3 称此项为「零锁定」。因 [8.4](#84-决策-4--分级输出保证与导出-bundle) 揭示的校验能力无法随 YAML 导出，**改称「低锁定」**——这是准确性修正，不是措辞软化。

星槎的 Agent 定义**就是** pydantic-ai 官方 `AgentSpec`，不是自有格式的转译。导出物是一个零星槎依赖的目录：

```
extract/
├── agent.yaml      # 纯 AgentSpec，pydantic-ai 直接可读
├── schema.json     # 输出 JSON Schema
└── run.py          # ~12 行校验 runner，仅依赖 pydantic-ai + jsonschema
```

```python
from pydantic_ai import Agent
agent = Agent.from_file("agent.yaml")     # 零星槎依赖
```

| | 导出后保留 | 导出后丢失 |
|---|---|---|
| 内容 | 模型 · 指令 · 内置能力 · 重试 · 模型参数 · schema（作为模型指令） | 运行时校验（需 `run.py` 补回）· 用量计量 · 配额 · 版本历史 |

**为什么抄不走** —— 不是工程成本，是战略成本。Dify、Flowise、Langflow、Open WebUI 的配置均为自有 schema；要达到同等可移植性，等于把自己的核心重写在别人的框架上。

**代价** —— 赌注押在 pydantic-ai 会持续赢（[R2](#9-风险)）。

**定级** —— 这是**优秀的采用理由，不是护城河**。它降低用户的决策风险，但不阻止竞品复制。

### 5.3 卖点乙：在声明式路径上恢复输出校验

**v0.3 的原话**：「pydantic-ai 原生：JSON Schema 强约束 + 校验失败自动重试」，标注为实机 probe 验证。该结论错误。

**精确事实**：pydantic-ai 的两条路径行为相反。同一份三重违规数据（缺必填 `score` · `title` 声明 string 实给 `12345` · `keywords` 声明 `maxItems:3` 实给 5 个）：

| 路径 | 写法 | 结果 | 模型调用次数 |
|---|---|---|---|
| **命令式（Python）** | `output_type=Article`（真 Pydantic model） | ✅ **拦截**，`Exceeded maximum output retries` | 3（重试已触发） |
| **声明式（YAML）** | `AgentSpec.output_schema` → `StructuredDict` | ❌ **放行**，输出为普通 `dict` | 1（重试未触发） |

根因：`output_schema` 被转成一个附带 JSON schema 的 `dict[str, Any]` 子类，schema 仅用于生成发给模型的指令，Pydantic 侧只校验"是不是 dict"。

**这不是框架缺陷，是声明式路径丢失了命令式路径已有的保证。**任何用 YAML 配置 Agent 的产品都会踩到同一个坑——包括星槎自己，如果不专门处理。

**因此本项的正确表述**：

> 星槎在声明式路径上**恢复**命令式路径的输出保证。用户在 Web 表单里填 schema，得到与手写 Pydantic model 同等强度的校验与重试。

**补救方案已实测可行**（[8.4](#84-决策-4--分级输出保证与导出-bundle)）：`output_validator` + `jsonschema` + `ModelRetry`。持续违规 → 3 次调用后正确抛错；先违规后修正 → 2 次调用自动恢复。

**竞品对照**（v0.3 依据旧 issue 断言「Dify 结构化输出确实不行」，该判断已过时）：

| 产品 | 现状 |
|---|---|
| **Dify** | 已有可视化 schema 编辑器 + JSON Schema 直写 + AI 生成。但官方明示"非原生 JSON 支持的模型只是把 schema 塞进提示词，结果可能不稳"，且重试针对**调用失败**而非 schema 违规 |
| **pydantic-ai 声明式** | 不校验（实测） |
| **Instructor** | 专做此事且成熟，但是库不是平台——无多用户、无计量、无 Web 配置。**若用户只要可靠抽取，它是比星槎更直接的答案** |
| **星槎** | 计划实现，**尚未实现，未做基准测试** |

**定级** —— 技术定位清晰，但**仍是待验证假设**。[11.3](#113-立项与技术验证门槛) 的多模型基准测试出数据前，不得作为卖点对外宣传。

### 5.4 卖点丙：Agent 进入客户端模型选择器

> v0.3 称「Agent 即 Model × 零中间件 + 硬配额，组合独有」。两处均需收窄：OpenRouter Presets **已可**直接以 `{"model": "@preset/slug"}` 调用；croit/llm-gateway 的**配额比星槎原规划更强**。

仅剩一点仍然成立且有实测支撑：

**被客户端自动发现。**Preset 可被调用，但实测**不出现在 `GET /v1/models`**（对全量模型目录逐条检查，零命中）。星槎的 Agent 出现在下拉框里——非技术同事在 Cherry Studio 里能直接看见并选中；Preset 需要事先知道 slug 并手工填写。这个差别对 [P1](#12-目标用户) 和场景 4 是决定性的，对开发者用户则可有可无。

| 能力 | 星槎 | Dify | Open WebUI | croit | New API | LiteLLM | OR Presets |
|---|---|---|---|---|---|---|---|
| 可作为 model id 调用 | ✅ | ❌ | ✅ | ❌ 无 agent | ✅ 仅模型 | ❌ | ✅ |
| 进 `GET /v1/models` 被自动发现 | ✅ | ❌ | ✅ | ✅ 仅上游模型 | ✅ | ❌ | ❌ 实测零命中 |
| 按用户强制配额 | ✅ | ✅ | ❌ 只报 token | ✅✅ **更强** | ✅ | ✅ | ❌ |
| 部署重量 | 单进程/SQLite | 8 容器 | 单容器含前端构建 | 单二进制/SQLite | 轻 | 需 Postgres | SaaS |
| 可导出脱离本平台 | ✅ | ❌ | 格式自有 | N/A | N/A | 部分 | ❌ |

**定级** —— **实用适配功能，不是护城河。**

### 5.5 降级与否决的卖点

| 原卖点 | 处理 | 原因 |
|---|---|---|
| 结构化输出"可靠" | **重写为待验证** | 实测推翻，见 [5.3](#53-卖点乙在声明式路径上恢复输出校验) |
| "零锁定" | **改称低锁定** | 校验能力无法随 YAML 导出 |
| "组合独有" | **删除** | OpenRouter Presets 与三个开源项目已覆盖大部分组合 |
| "市场空当已确认" | **改为尚未验证的窄切口** | 交集已有三个项目占位 |
| "数据不出境" | **删除** | 走 OpenRouter 时数据必然出境，自持的只是控制面 |
| 提示词经济学 / 换模型省钱模拟 | **否决** | Langfuse 已内建按 prompt 版本聚合成本、延迟、token、评分与灰度 |
| 装完即用 · 单目录数据 · 能力自动生长 · 大陆可用性 | **降级为执行质量** | 一个周末可抄的 CRUD，不该占据核心卖点位置 |

**取证二 · 官方服务化 PR 的关注度。**[PR #5949](https://github.com/pydantic/pydantic-ai/pull/5949)（`Agent.to_openai_responses()`，把 agent 暴露为 OpenAI Responses 端点）获得 **0 个反应**，处于待维护者审核状态。这是最接近星槎功能的官方动作，社区反响为零。

## 7 技术底座

*本章回答：技术可行性，以及哪些轮子已经现成。*

### 7.1 实测关键事实

全部来自实机 probe，非文档转述。每条直接影响实现方案。

**关于 Agent 定义**

| 事实 | 对设计的影响 |
|---|---|
| `Agent.from_spec()` / `Agent.from_file(path, fmt='yaml')` 原生支持 dict/YAML/JSON 构造 Agent | 星槎**不发明配置格式**；Web 表单产出 `AgentSpec` dict 直接喂入。这是卖点甲的技术基础 |
| `AgentSpec` 字段：`model`(必填) `name` `description` `instructions` `deps_schema` `output_schema` `model_settings` `retries` `end_strategy` `tool_timeout` `metadata` `capabilities` `json_schema_path`（文档另列 `instrument`） | 表单字段与之一对一映射（[3.2](#32-管理员视角agent-配置面)） |
| YAML spec 需 `pydantic-ai-slim[spec]` extra，否则 `ImportError: PyYAML is required` | 依赖声明不可遗漏 |

**关于输出校验（v0.3 此处结论错误）**

| 事实 | 对设计的影响 |
|---|---|
| 两条路径行为相反：`output_type=<真 Pydantic model>` **拦截并重试**；`AgentSpec.output_schema` → `StructuredDict` **放行**。同一份三重违规数据（缺必填 / 类型错 / 超 maxItems），前者 3 次调用后抛 `UnexpectedModelBehavior`，后者 1 次调用直接通过 | 声明式路径丢失了命令式路径的保证，星槎必须自己补。代价分析见 [12.2](#122-最重要的发现约束解码不是免费的)，方案见 [8.4](#84-决策-4--分级输出保证与导出-bundle) |
| `output_validator` + `jsonschema` + `ModelRetry` 实测有效，但它是 Python 装饰器，**无法写进 YAML** | 卖点甲与卖点乙的结构性张力来源 |

**关于能力与扩展**

| 事实 | 对设计的影响 |
|---|---|
| YAML 可声明 capability 仅 14 个内置项：`Thinking` `Instrumentation` `WebSearch` `WebFetch` `ImageGeneration` `XSearch` `MCP` `ToolSearch` `PrefixTools` `NativeTool` `IncludeToolReturnSchemas` `SetToolMetadata` `RaiseContentFilterError` `ReinjectSystemPrompt` | 勾选项运行时从 `CAPABILITY_TYPES` 读取，不硬编码 |
| 官方明确：**Python 定义的 tools/toolsets 无法从 YAML 引用**（"take non-serializable arguments … can only be used in Python code"） | 这就是逃生舱要填的洞 |
| 自定义 capability 继承 `Capability`（dataclass，可绑 tools/toolsets/instructions）或 `AbstractCapability`，经 `custom_capability_types=[...]` 注入；注册表用 `setdefault` 合并，故可覆盖内置项 | 逃生舱实现路径确定 |
| capability 的 YAML 语法为 `- <CapName>` 或 `- <CapName>: {args}`，实例化为 `cls(*args, **kwargs)`。写作 `- name: Thinking` 会报错 | 实测踩坑；表单生成器必须产出正确形状 |

**关于上游与计量**

| 事实 | 对设计的影响 |
|---|---|
| 官方 `OpenRouterProvider` 已存在，`app_url` / `app_title` 自动注入 `HTTP-Referer` / `X-Title`；读取 `OPENROUTER_API_KEY` / `OPENROUTER_APP_URL` / `OPENROUTER_APP_TITLE` | 无需手写 `extra_headers` |
| `model: "openrouter:openai/gpt-5"` 前缀写法可用 | 表单中「模型」即一个字符串 |
| openai SDK 3.5 已迁至 `httpx2`（`github.com/pydantic/httpx2`，Pydantic 自家下一代客户端），plain `httpx` 不再安装 | HTTP 栈随 pydantic-ai 传递引入，**不额外引第二套栈** |
| `genai-prices` 随 pydantic-ai 一同安装。实测 `calc_price(Usage(input_tokens=10000, output_tokens=2000), model_ref="openai/gpt-5", provider_id="openrouter")` → **$0.0325**，认识 OpenRouter，价格表可在线更新 | **费用预估零自研**，不维护价格表 |
| `RunUsage` 字段：`input_tokens` `output_tokens` `cache_read_tokens` `cache_write_tokens` `input_audio_tokens` `output_audio_tokens` `cost` `requests` `tool_calls` `details` | 计量表结构照此设计，含缓存与音频维度 |
| 官方并发原语已有：`Agent(max_concurrency=...)` · `limit_model_concurrency()` · `UsageLimits` | 限流不必自研令牌桶 |

### 7.2 技术选型

| 层 | 选择 | 关键理由 |
|---|---|---|
| Python | 3.12+（开发 3.13） | pydantic-ai 要求 ≥3.10；3.12+ 的 typing 与 TaskGroup 更好用 |
| Agent 内核 | `pydantic-ai-slim[openai,spec]`，锁 `~=2.35.3` | 唯一提供官方声明式 `AgentSpec` 的框架 |
| 上游 | OpenRouter（官方 `OpenRouterProvider`） | 一个 key 通全部模型 |
| HTTP | `httpx2`（传递依赖，共享单实例） | 不引第二套栈 |
| Web | FastAPI + uvicorn | Pydantic 原生 · SSE 成熟 |
| 前端 | Jinja2 + HTMX + 内嵌静态文件 | **零 Node 构建链**，保住 C3 |
| 存储 | SQLite(WAL) + aiosqlite；SQLAlchemy 2.0 async + Alembic 启动时自动 `upgrade head` | 满足 C1 |
| CLI | Typer | 类型注解即参数 |
| 密钥 | cryptography Fernet；主密钥取 `XINGCHA_SECRET_KEY`，缺失则首启生成 `data/secret.key` 并 chmod 600 | OpenRouter key 不明文落库 |
| 费用 | `genai-prices` | 见 [7.1](#71-实测关键事实) |
| 可观测 | OpenTelemetry → 自部署 Langfuse OTLP，`Instrumentation` capability 一行开启；**不配置也能跑** | 提示词版本成本分析交给 Langfuse，不重复实现 |
| 质量 | ruff + pyright + pytest-asyncio + pydantic-ai `TestModel` / `FunctionModel` | LLM 相关测试必须离线可跑 |

## 8 关键架构决策

*本章回答：三个岔路口选了哪条，代价是什么。*

### 8.1 决策 1 · 逃生舱默认走 MCP，而非进程内代码引用

官方 YAML 无法引用 Python 工具，星槎必须补上。两条路径：

| 方案 | 可移植性 | 隔离性 | 延迟 | 调试 |
|---|---|---|---|---|
| A. 自定义 capability 进程内加载 `python:` 符号 | ❌ 导出的 YAML 需 `custom_capability_types`，脱不了星槎 | ❌ 用户代码崩溃影响主进程 | 最低 | 简单 |
| **B. 星槎内置本地 MCP server 承载用户工具，YAML 用官方 `MCP` 能力声明** | ✅ `MCP` 是官方可声明能力，**导出的 YAML 100% 纯净** | ✅ 独立进程 | +数毫秒 | 链路稍长 |

**决定：B 为默认，A 保留为可选快路径。**

理由：

1. B 使逃生舱**不破坏卖点甲** —— 用了自定义工具的 Agent 导出后仍是纯 pydantic-ai spec。
2. 用户的 Python 工具成为标准 MCP server，可被 Claude Code、Cursor 等任意 MCP 客户端复用。
3. 自定义代码运行在独立进程，崩溃不拖垮网关。
4. 本地 MCP server 由星槎自行 spawn 并随包分发，**不违反 C1**。

### 8.2 决策 2 · Agent 定义整块存 JSON，不拆列

`AgentSpec` 字段会随 pydantic-ai 演进，拆列意味着每次上游变动都要迁移。整块 JSON + Pydantic 校验最稳，且所有版本适配集中在 `builder.py` 单个文件——这同时是 [R2](#9-风险) 的缓解手段。

### 8.3 决策 3 · 结构化输出的 Agent 拒绝 `stream=true`

返回明确 400，而非流一半 JSON 让客户端解析失败。要流式就用纯文本 Agent。

**原则**：诚实报错优于假装支持。

---

### 8.4 决策 4 · 分级输出保证与导出 bundle

本节是**输出保证的唯一权威定义**，[5.3](#53-卖点乙在声明式路径上恢复输出校验) 说明其价值，[12.2](#122-最重要的发现约束解码不是免费的) 给出文献依据。

**问题**：声明式路径不校验；而校验手段（`output_validator`）是 Python，写不进 YAML，与卖点甲的可移植性冲突。且文献证明约束解码本身有代价，不能无脑选最强档。

**四档保证**。星槎按模型能力自动判定可用档位，在表单上显式标注代价，由用户选择：

| 档 | 机制 | 形状保证 | 内容风险 | 成本 | 适用 |
|---|---|---|---|---|---|
| **T1** 原生约束 | 透传 `response_format: json_schema` | 最强 | **有对齐税**，推理密集任务可能退化 | 单次 | schema 与正确性无关的抽取 |
| **T2** 校验重试 | `output_validator` + jsonschema + `ModelRetry` | 强 | 无对齐税 | 重试放大 | 推理密集、schema 复杂 |
| **T1+** 两阶段 | 自由推理 → 再格式化 | 最强 | 最低 | 约两倍 | 内容正确性 > 成本 |
| **T3** 仅提示 | schema 进提示词 | 无 | 无 | 单次 | 用户显式关闭 |

判定依据实测可得：OpenRouter `/v1/models` 的 `supported_parameters` 字段。2026-08-28 快照：381 个模型中 295 个含 `structured_outputs`，86 个不含（**目录随时变动，比例比绝对值更有意义**）。

**导出 bundle**。T2 的校验逻辑随导出物一起走，保持零星槎依赖：

```
extract/
├── agent.yaml      # 纯 AgentSpec
├── schema.json     # 输出 JSON Schema
└── run.py          # ~12 行，仅依赖 pydantic-ai + jsonschema
```

```python
# run.py —— 无任何 xingcha import
import json, jsonschema
from pydantic_ai import Agent, ModelRetry

agent  = Agent.from_file("agent.yaml")
schema = json.load(open("schema.json"))

@agent.output_validator
def _validate(data):
    try:
        jsonschema.validate(data, schema)
    except jsonschema.ValidationError as e:
        raise ModelRetry(f"输出不符合 schema: {e.message} (路径 {list(e.absolute_path)})")
    return data
```

**必须配套的护栏**：重试放大 token 与费用。需限制重试次数、单次运行 token 上限（`UsageLimits`）与费用上限，并把「因 schema 违规而重试」单列为可观测指标——否则坏 schema 会静默烧钱。

**诚实表述**：导出物保留全部能力，但不是单个 YAML 而是三文件目录。这是「低锁定」而非「零锁定」的确切含义。

## 10 价值判断

*本章回答：到底值不值得做，以什么身份做。*

### 10.1 评分

| 维度 | 评分 | 依据 |
|---|---:|---|
| 自用价值 | **8 / 10** | 确实省掉重复搭建服务层的工作，需求由真实痛点逼出 |
| 开源价值 | **6 / 10** | 有明确但较窄的 pydantic-ai 用户群 |
| 当前差异化 | **4 / 10** | 有特点，但"组合独有"已被证伪 |
| 当前商业价值 | **3 / 10** | 无付费需求证据，且存在 [R8](#9-风险) 的商业错位 |
| 技术可行性 | **7 / 10** | 能做，但核心校验方案需自建，非框架自带 |

### 10.2 结论

**作为自用工具：价值确凿。**需求由两件真实的事逼出——大陆访问 OpenRouter 受限，以及 Dify 对"我只想把提示词变成一个能调的端点"过重。做出来自用，顺带吃透 pydantic-ai，这笔账划算。

**作为开源项目：一个尚未验证的窄切口。**会有人用，但大概率是小众技术用户；多数普通团队会选择更成熟的产品。

**作为商业产品：不建议按 v0.3 全量范围立项。**

**用户实际会怎么选**（诚实推演）：

| 场景 | 更可能选择 | 星槎胜出的条件 |
|---|---|---|
| 只有一两个 pydantic-ai Agent | `pydantic-ai-server` 或自写 FastAPI | 需要多用户、后台、版本、额度 |
| 非技术人员聊天 / 知识库 / RAG | Open WebUI / Dify | 明确拒绝重部署与平台格式 |
| 主要管理 Key、预算、路由 | LiteLLM / New API / croit-gateway | 同时需要受管提示词与 AgentSpec |
| 已在用 OpenRouter | **OpenRouter Presets** | 必须自部署或要求可迁移 |
| 程序化结构化抽取 | Pydantic `output_type` / Instructor | 星槎能用基准测试证明更稳 |
| 受监管企业 | 企业版网关 | 补齐 SSO、审计、备份、SLA、HA |

## 11 实现计划

*本章回答：先做什么，以及在什么条件下才继续做。*

### 11.1 路线选择

| 路线 | 内容 | 成本 | 评价 |
|---|---|---:|---|
| A. 按 v0.3 全量开发 | 独立通用 Agent 平台 | 50–80 人日 | ★ 范围过大、竞品强、核心假设曾出错 |
| **B. 窄版 pydantic-ai 控制面** | 只补管理、配额、导出、校验 | **10–15 人日 Alpha** | **★★★★★ 采用** |
| C. 垂直结构化抽取产品 | 卖"可靠抽取结果" | 中高 | ★★★★ 若访谈发现用户只在乎合同/工单/简历抽取，转此路线 |

> v0.3 给出的"M0–M7 合计 11 人日"是**乐观估计**，且它对应的是路线 A 的范围。此处修正：11 人日对应路线 B 的 Alpha，路线 A 需 50–80 人日。

### 11.2 Alpha 范围（路线 B）

只做证明论点所必需的部分：

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **A0** | 骨架 · config · SQLite + 迁移 · `/healthz` | `xingcha serve` 起得来 |
| **A1** | agent 表 + builder + runner + `/v1/chat/completions` + `/v1/models` | curl 以 OpenAI 格式调通纯文本 Agent |
| **A2** | **分级输出保证**：查 `supported_parameters` 判定 T1/T2；T1 透传 `response_format`，T2 走 `output_validator` + jsonschema + ModelRetry + 重试护栏 | 违规输出被拦截并重试；耗尽后明确报错；表单显示当前模型的保证等级（[12.2](#123-采纳方向一--分级输出保证含代价标注)） |
| **A3** | 用户 · 令牌 · **三级硬配额** | 超配额返回 429，50 并发下不穿透 |
| **A4** | 计量与费用：run/run_usage + genai-prices + 用量视图 | 数字与 OpenRouter 后台同量级 |
| **A5** | Web 表单建 Agent（最小版：基本 + 提示词 + 模型 + 输出 + 能力勾选）+ **schema 字段命名 lint**（[12.4](#124-采纳方向二--schema-字段命名-lint新增成本极低)） | 全程不碰 YAML 建出并跑通一个 Agent；字段名过短或无语义时给出改写建议 |
| **A6** | **导出 bundle 并验证脱离星槎可运行** | 干净环境中用导出物跑通，含校验行为 |

**Alpha 明确不做**：多轮 session · 多模态 · 流式 · 8 个模板 · MCP 逃生舱 · Langfuse · Docker 发布。这些等验证通过再做。

### 11.3 立项与技术验证门槛

**技术门槛**（Alpha 内必须完成，否则卖点站不住）：

1. **多模型结构化输出基准** —— **直接采用 [SOB 基准](https://arxiv.org/abs/2604.25359)**（[12.6](#126-采纳方向四--直接采用现成基准不自建)），不自建数据集。至少 5 个主流模型，覆盖四个维度：
   - **T1 / T2 / 两阶段三种模式对比**（验证[对齐税](#122-最重要的发现约束解码不是免费的)在本场景是否成立）；
   - **T1 vs T2 的一次通过率与重试成本**（证明分级保证的价值）；
   - **schema 合规率 vs 内容准确率**（验证 [Let Me Speak Freely](https://aclanthology.org/2024.emnlp-industry.91/) 的退化结论在本场景是否成立）；
   - **两阶段模式是否真的提升准确率**（决定 [12.3](#122-最重要的发现约束解码不是免费的) 是否实现）。
   **这是卖点乙唯一的证明。**
2. **客户端兼容矩阵** —— Cherry Studio、Open WebUI、Continue、Cursor 的具体版本，记录哪些能自动发现 Agent。
3. **50 并发下配额不穿透**。
4. **干净环境导出物可运行**。

**产品门槛**（决定是否从自用工具转为认真做产品）：

- 10 次真实问题访谈；
- 3 个愿意交出真实 Agent、Schema 与调用方的试点；
- 至少 2 个试点第二周仍在主动使用；
- 至少 1 个愿意为部署、支持或 OEM 付费。

> **停止信号**：若试点用户首先要求的是 RAG、DAG、知识库或聊天 UI，则停止做独立平台——他们最终仍会选择 Dify 或 Open WebUI。

### 11.5 部署形态

单机三种：`uv tool install` · 单 Docker 镜像 · docker-compose（可选带自部署 Langfuse）。

大陆访问 OpenRouter 受限时，中转层**不自研**——Caddy 反代起步，需分发额度再上 New API，星槎侧只需把 `OPENROUTER_BASE_URL` 指过去。

> **反代有一处致命坑**：Caddy 默认自动注入 `X-Forwarded-For`，必须显式 `header_up -X-Forwarded-For` 抹除，否则客户端真实 IP 直接交给上游，中转形同白建。

| Q7 结构化抽取可靠性 | 32 | 18 |
| Q8 已拒方向的代价证据 | 200 | 144 |

> **Q2 只有 2 篇本身就是发现**：「格式约束是否损害质量」这个对星槎最要害的问题，学界系统研究极少。这意味着相关决策只能建立在薄证据上，必须自己做基准测试。

### 12.2 最重要的发现：约束解码不是免费的

**上一版本文档的错误。**v1.0 的 12.2 把「T1 原生约束解码」描述为"生成即合规、零重试成本"的最强保证。**文献否定了这个表述**——它在"形状正确"上确实最强，但存在系统性代价。五条独立证据：

| 证据 | 发现 |
|---|---|
| [2604.06066](https://arxiv.org/abs/2604.06066)《结构雪球：约束解码的对齐税》 | 用 Outlines 强制结构化反思**未改善**自我纠错，反而触发新失败模式"structure snowballing"：满足格式规则的认知负荷把模型推入格式陷阱，**表面语法近乎完美，却检测不出深层语义错误** |
| [2408.02442](https://aclanthology.org/2024.emnlp-industry.91/)《Let Me Speak Freely?》(EMNLP 2024) | 格式约束显著降低推理能力，**约束越严退化越明显** |
| [2606.01926](https://arxiv.org/abs/2606.01926) | 局部约束解码的近视 masking 导致**采样有偏与性能退化**，需 SMC 等昂贵方法缓解 |
| [2608.10137](https://arxiv.org/abs/2608.10137)《The Parser Already Knows》 | 刚性 masking **扭曲模型概率分布**，偏向"合法但次优"的输出；在线采样可还原但计算昂贵——**质量与延迟被迫二选一** |
| [2608.13959](https://arxiv.org/abs/2608.13959)《Repair, Not Improvement》 | 在工具调用弃权场景，约束解码相对无约束**在六个条件中四个为负，最差 −29.5 分**。并指出 grammar 同时干两件事（限制 token + 决定何时停止），**两者符号相反**；且警告：当约束编码的是**正确性要求**而非格式要求时，不可外推既有结论 |

**对星槎的修正**：

> T1 不是"最强保证"，而是"**形状保证最强、内容保证可能最弱**"。分级输出保证的正确表述是：**让用户知道自己在哪一格，以及那一格的代价是什么**——而不是无脑推荐 T1。

这同时说明 v1.0 把「12.2 分级保证」和「12.3 两阶段」列为两条独立建议是错的：**它们是同一个权衡的两面**，应合并为一条设计主线。

### 12.3 采纳方向一 · 分级输出保证（含代价标注）

文献的直接产物：**四档保证机制**（T1 原生约束 / T2 校验重试 / T1+ 两阶段 / T3 仅提示），完整定义见 [8.4](#84-决策-4--分级输出保证与导出-bundle)。

相对 v1.0 的关键修正是**呈现方式**：不替用户选"最强"，而是把四档的形状保证、内容风险、成本摆出来标注。这正是控制面该提供的价值——竞品无一这么做，Dify 只在文档里写一句"结果可能不稳"就把判断责任丢给用户。

### 12.4 采纳方向二 · Schema 字段命名 lint（新增，成本极低）

[2604.14862](https://arxiv.org/abs/2604.14862)《Schema Key Wording as an Instruction Channel》给出一个此前完全未预料的结论：

> 在 prompt、模型、输出结构、解码设置**全部固定**的前提下，**仅改变 schema 字段的措辞，就能显著影响准确率**。schema key 本身是一条隐式指令通道。且效应与模型相关：Qwen 系更受 schema 层指令影响，LLaMA 系更依赖 prompt 层。

**这对星槎近乎量身定制**：用户在 Web 表单里定义输出字段，星槎完全有条件在保存时给出提示——字段名过短、无语义、纯缩写时警告，并给出改写建议。实现成本极低（一组规则 + 提示文案），却是**一个有论文背书、竞品完全没有、且只有"表单建 Agent"这种形态才方便提供**的功能。

### 12.5 采纳方向三 · 校验驱动的模型升级（结论不变）

Q4 检索到 116 篇路由/级联文献（104 篇为 2025 年后），确认这是极活跃领域。但结论与 v1.0 一致：

- **通用学习式路由不采纳** —— 需偏好数据训练路由器与额外评分模型，违反 C1/C2，且踩[非目标](#23-非目标)；
- **窄化版成立** —— 星槎已有确定性质量信号（schema 校验结果），级联无需任何额外模型，只是把重试循环的"再试一次"改成"换更强的模型再试一次"。

适用边界仍需诚实标注：只对**校验可判定**的场景有效，对自由文本问答无能为力。

### 12.6 采纳方向四 · 直接采用现成基准，不自建

[2604.25359](https://arxiv.org/abs/2604.25359)《The Structured Output Benchmark (SOB)》正好覆盖 [11.3](#113-立项与技术验证门槛) 所需，且明确指出现有基准的缺陷正是星槎要测的维度：

> 现有结构化输出基准**要么只看 schema 合规，要么只在单一域评估值正确性**。

SOB 提供多源语料（5000 条文本 / 209 条 OCR 图像 / 115 条音频），并刻意把结构化输出能力与视觉、语音处理质量解耦。

**决策**：[11.3](#113-立项与技术验证门槛) 的基准测试**直接采用 SOB**，不自建数据集。这把该门槛的成本从"数周"降到"数天"。

### 12.7 新增风险 · 用户自定义 schema 是攻击面

[2606.11817](https://arxiv.org/abs/2606.11817)《Grammar-Constrained Decoding Can Jailbreak LLMs》揭示一个反直觉风险：

> GCD 这项**以可靠性为目的**的技术本身可成为攻击面。攻击手法 CodeSpear 表明，仅施加一个**良性的**代码 grammar 约束即可越狱模型生成恶意代码。

**对星槎的直接影响**：星槎让用户在 Web 表单里自由定义 JSON Schema，而该 schema 会被透传为约束条件。这意味着**用户提交的 schema 是一个未受审查的攻击输入**，此前的[安全模型](#36-逃生舱)只考虑了"不执行用户提交的 Python"，未考虑 schema 本身。列为 R11。

### 12.8 明确拒绝的方向（含文献依据）

Q8 检索到 200 篇相关文献，用于检验拒绝理由是否成立——**拒绝也需要证据，否则只是偏见**。

| 方向 | 文献量 | 拒绝理由 |
|---|---:|---|
| **学习式通用路由** | 116 | 领域极活跃且方法快速迭代（2026 年仍在大量产出 bandit、RL、校准等新路由方法），意味着任何自研实现会迅速过时；且需额外模型，违反 C1/C2 与非目标 |
| **语义缓存 / 前缀缓存** | 95 | 大量工作聚焦 KV cache 复用与 GPU 侧优化——**星槎调用的是 API，不持有 KV cache，这类成果基本用不上**；语义缓存则需向量库，违反 C1 |
| **自动提示词优化** | 134 | 需标注数据集与大量试跑；是 Agenta / Dify / Langfuse 战场；违反 C4 |
| **不确定性 / 幻觉检测** | 157 | 主流方法（语义熵等）需多次采样，成本成倍；且属评估领域，Langfuse 已覆盖 |
| **多租户 GPU 调度** | 37 | 检索发现该领域**几乎全部关于 GPU 侧推理服务**（chunked-prefill、LoRA 服务、异构调度）。**星槎不服务模型，只转发 API，这些成果不适用**——星槎的配额设计得不到学界助力，只能工程化解决 |

> 最后一条是本次调研的一个**负面但有价值的发现**：学术界的"多租户 LLM 服务"与星槎需要的"API 网关级配额"是两个不同问题，不要指望文献支撑。

### 12.9 优先级

| 方向 | 强化 | 成本 | 时点 |
|---|---|---|---|
| 12.3 分级保证（含代价标注） | 卖点乙 | 低，数据现成 | **Alpha（A2）** |
| 12.4 Schema 字段 lint | 卖点乙 | **极低** | **Alpha（A5 表单）** |
| 12.6 采用 SOB 基准 | 验证门槛 | 低 | **Alpha 门槛** |
| 12.7 schema 攻击面防护 | 安全 | 中 | Alpha 后 |
| 12.5 校验驱动升级 | 成本控制 | 中 | Alpha 后 |

**共同点**：全部围绕**输出保证**主线，无一开辟新战场。能通过筛选恰恰因为定位够窄——窄到能判断什么该拒绝。
