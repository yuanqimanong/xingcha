## 0 摘要

**两个真实的上线点，不是一个。**

| 版本 | 代号 | 工期 | 上线后你立刻能做什么 | Dify 状态 |
|---|---|---:|---|---|
| **v0.1** | 渡口 | **14 人日** | 本地与业务代码把 `base_url` 指向新加坡，用一把 `sk-xc-` key 调**任意 OpenRouter 模型**，流式非流式都通，**代理彻底不进代码**；浏览器里有一个能看的后台：总览、密钥管理、调用记录 | 继续留着 |
| **v0.2** | 载物 | **+10 人日** | 把 Dify 里的提示词搬成星槎 Agent（表单里建，带 JSON Schema），业务代码把 `model` 从 `openai/gpt-5` 改成 `extract`，200 即保证符合 schema | **可整套关停** |
| v0.3 / v0.4 | — | +10 人日 | 四档保证补齐 · 导出 bundle · 配额 · 多用户 · 真流式 · 可观测 | — |

**为什么拆成两个上线点。** 你提了三件事：尽快出一版部署上线、第一版要有 UI、上线后 key 与调用方式永不变。这三件事里前两件有张力——完整的 Agent 面（builder + 输出保证 + 表单编辑器）是全项目最难的一段，等它做完再上线就不叫"尽快"。所以 v0.1 先把**你的第一性痛点**（不挂代理）和**后台 UI 骨架**交付掉，Agent 面在 v0.2 落。UI 从 v0.1 就存在且设计系统在那时定型，v0.2 的 Agent 表单只是往同一套骨架里加页面。

> 如果你更愿意"憋一版一次上线"，把 v0.1 与 v0.2 合并即可，工期 24 人日、只上线一次。这是你的取舍，我按两段做除非你说合并。

**最重要的一句话**：v1 交付的不是功能清单，是一份**此后只能加、不能改**的对外契约。所有"推后会毁约"的东西（路径归属、token 格式、model 命名空间、错误码、响应形状、数据库前向兼容）全部压进 v0.1；所有"以后加不破坏兼容"的东西一律后置。清单见 [第 3 节](#3-契约冻结清单v01-必须定死)。

**两份计划草案共同漏掉、但必须在公网暴露前落地的高危项有 10 条**，其中 CSRF 与"测试连接"的 SSRF 组合起来就是一次点击盗走你的 OpenRouter key。见 [第 4 节](#4-公网暴露的准入清单v01-的硬门槛)。

## 2 实机探测推翻了文档的哪些设计

6 组探测在真实 venv 里跑代码验证了既有两份文档的承重断言。**20 处需要修正**，下面只列会改动实现的。每条都有可复现的实测证据。

### 2.1 会让文档代码直接跑不通的硬伤

| # | 文档写法 | 实测结果 | 正确做法 |
|---|---|---|---|
| **H1** | `代码架构实现.md` §5.2 builder：`spec.pop("output_schema", None)` 后交给 `from_spec` | `from_spec` 走 `else` 分支把 `output_type` 退化成 `str`，于是 `output_validator` 收到的是**原始 JSON 字符串**，`jsonschema` 对 object schema 必然报 `is not of type 'object'`——**连完全合法的模型输出都会被打到 `Exceeded maximum output retries`** | 必须把 `output_type=output_spec(tier, schema)` **传进** `from_spec`（实测 `from_spec` 的 20 个关键字里确有 `output_type`）。`pop` 本身不必要 |
| **H2** | §5.4 T2 = `ToolOutput(sd)`，四档表标注「无对齐税」 | pydantic-ai 会按 model profile **自动把 `strict` 推断成 `true`** 并主动注入 `additionalProperties: false`，于是 T2 在 OpenAI 系模型上**同样承担对齐税**，且是否触发取决于用户 schema 长什么样（全字段必填就触发） | T2 必须显式写 `ToolOutput(sd, strict=False)`，否则前端给你显示的"保证等级"是假的 |
| **H3** | §5.6 schema_guard：`if "$ref" in ...: raise SchemaRejected("不支持 $ref / $defs")` | pydantic-ai 内部用 `InlineDefsJsonSchemaTransformer` **内联展开** `$defs`，非递归引用是支持的。文档护栏把合法 schema 挡在门外，同时**漏掉了真正会崩的两种**：悬空 `$ref`（裸 `KeyError`）与非 object 根 schema（`UserError`） | 删掉整体拒绝，改成 `StructuredDict(schema)` + `TypeAdapter(...).json_schema()` 探测式校验。**并且校验器必须用内联展开后的 schema**——否则 validator 用带 `$ref` 的原文、模型收到展开版，两边不是同一份约束。展开结果要落库进 `agent_version.out_schema` |
| **H4** | §5.2 `max_concurrency=16` 传给每次请求新建的 Agent | 信号量是**每个 Agent 实例私有**的。实测两个各限 1 的 Agent 并发峰值＝2，即完全不封顶；传同一个 `ConcurrencyLimit` **配置对象**也不共享 | 收一个**进程级 `ConcurrencyLimiter` 单例**（注意是 Limiter 不是 Limit），在 app lifespan 里创建。文档的 R10 缓解措施按原写法根本不成立 |
| **H5** | §5.8 `_to_openai(r)` 里读 `r.cost_usd` / `r.tier` / `r.schema_retries` | `AgentRunResult` 上这三个属性 `hasattr` 全是 `False` | 入参必须是星槎自有的 `RunOutcome` 包装类型并加类型标注，否则是个只在运行时炸的静默 `AttributeError` |

### 2.2 直接关系到你的部署环境的三条

| # | 事实 | 后果 | 处理 |
|---|---|---|---|
| **E1** | `httpx2` 默认 `trust_env=True`，会读机器的 `ALL_PROXY` / `HTTP_PROXY` | 你本机现在就有 `ALL_PROXY=socks5://192.168.183.1:7890`。socks5 下 `OpenRouterProvider()` 在**构造阶段**直接 `ImportError`（socksio 未装），服务起不来，且报错完全看不出跟代理有关 | 所有自建 client 一律显式 `trust_env=False`；`test_no_proxy_dependency` 在 `ALL_PROXY` 指黑洞的环境下跑全套离线测试，锁进 CI |
| **E2** | `OPENROUTER_BASE_URL` **不被官方读取**（源码里 `os.getenv` 只有 `OPENROUTER_API_KEY` / `_APP_URL` / `_APP_TITLE`） | `前期调研.md` §11.5「星槎侧只需把 `OPENROUTER_BASE_URL` 指过去」为假 | 中转只能靠自建 `AsyncOpenAI(base_url=...)` 注入。且**传了 `openai_client=` 后官方不再注入 `HTTP-Referer`/`X-Title`**，文档 builder 里手写 `default_headers` 是必需的、不是冗余 |
| **E3** | `AsyncOpenAI` 默认 `max_retries=2` | 实测 timeout=0.3 会把墙钟放大到 2.17s 并**把中转打三遍** | 显式 `max_retries=0`，重试交给 pydantic-ai 的 retries/guarantee 层 |

### 2.3 计价与计量（影响账单可信度）

| # | 文档假设 | 实测 | 处理 |
|---|---|---|---|
| **P1** | `genai-prices` 覆盖 OpenRouter，「费用预估零自研」 | 拿今天 OpenRouter 在售的 **424** 个模型逐个跑 `calc_price`：成功 **283 / 424 = 66.7%**，抛 `LookupError` **141 个**。跑在线更新后覆盖率**一个都没多**（上游数据滞后，不是本地快照过期），漏的全是新模型与 `:free` / `:batch` 变体 | **`/v1/models` 响应自带精确价格且 424/424 全有**，抽样与 genai-prices 完全相等 → **把 catalog pricing 升为主价源**，genai-prices 降为回落 |
| **P2** | `pricing.py` 只把 `input_tokens`/`output_tokens` 传给 `calc_price` | 丢掉 `cache_read_tokens`，而两边都是**包含式**语义（cache_read 是 input 的子集，按 cache 单价重算）。同一次调用**高估 16%**（0.0325 vs 0.0280），正好撞上文档的 R7 信任危机 | 把 `RunUsage` 整个直传（它满足 `AbstractUsage` 协议），不做任何减法 |
| **P3** | pydantic-ai 自动填的 `usage.cost` 是「上游返回的真实费用」 | **假**。填的是 genai-prices 的估价；OpenRouter body 里真实的 `cost` 因为是 float 被 `_map_usage` 的 `isinstance(v, int)` 过滤掉，**哪儿都没留** | `cost_source` 从第一天就是**四态**（`openrouter_catalog` / `genai_prices` / `upstream` / `unknown`），v1 只会出现前两种和 unknown；UI 一律标「预估」；`upstream` 留给 v0.4 的 httpx2 event hook 对账 |
| **P4** | `run_usage.cost_usd REAL` | 金额用 float 存不住 Decimal；`RunUsage.cost` 实际是 `Decimal \| None`，`None`（无法定价）与真实的 0 费用必须可区分 | 列改 `TEXT`（存 Decimal 的 str），`NULL ≠ 0`；全链路 Decimal |

### 2.4 保证档与重试（卖点乙的实现细节）

| # | 修正 |
|---|---|
| **G1** | 命令式路径的模型调用次数是 `1 + retries`，**不是文档表格里的 3**（实测 retries=3 → 4 次）。这个数字直接进成本模型：T2 最坏是 **4 倍** token 而非 3 倍，配额 worst-case 预留按 4x 算 |
| **G2** | 「T3 不校验 / T1 只做断言」在**框架层面完全不存在**——四种输出模式下 `output_validator` 被调用次数逐位相同。这纯粹是星槎 `apply_guarantee` 里提前 return 造成的**应用层策略**。所以 `test_t3_does_not_validate` 必须断言「本项目没有注册 validator」（`agent._output_validators == []`）+「BAD payload 原样放行」，而不是断言框架行为——按文档现在的写法，任何人把 T3 误传成 T2 都测不出来 |
| **G3** | 文档的 `counter["schema_retries"] += 1` 在**重试耗尽时多计 1**（retries=2 → 真实重试 2 次但计到 3），正好在最需要精确告警的失败 run 上系统性偏移一格。拆成两个：`schema_violations`（自己数违规次数）与 `schema_retries`（读 `ctx.retry` 拿框架的真实序号），validator 改 `(ctx, data)` 两参形态 |
| **G4** | `retries` 有**四个生效位点**，优先级：`ToolOutput(max_retries=)` > `run(retries=)`/`run(spec=)` > `from_spec` kwarg > `AgentSpec.retries` > 默认 **1**。2.35.3 新增的 `retries={'tools': N}` **不影响** output 校验重试——表单必须落成裸 int 或 `{'output': n}`，builder 里加断言 |
| **G5** | `UsageLimits.request_limit` 默认是 **50 不是 None**，且它计的是**所有**模型请求（工具往返也算）。文档的 `request_limit = max_retries + 1` 会把任何带工具的 Agent 误杀成"限流"错误。公式改 `(max_retries + 1) + max_tool_steps` |
| **G6** | `cost_limit` 存在且真能拦，但对 genai-prices 认不出的 model **静默失效**（只发一条 `CostNotFoundWarning`）。由 P1 可知这是 1/3 的模型 → **`total_tokens_limit` 从可选变必填**，作为永远可执行的硬兜底；`cost_limit` 只作辅助，且必须 `Decimal(str(...))` |
| **G7** | T1 的 `strict=True` 会**静默改写用户 schema**：所有可选字段被强行塞进 `required`（且不加成 `["integer","null"]`）。「T1 透传 response_format」的措辞对用户构成隐性违约，改成「T1 以 strict 模式提交 schema，可选字段会被上游提升为必填」，并在 schema_lint 里保存时就提示 |
| **G8** | 判档**只能看 `structured_outputs`，不能看 `response_format`**——今天 424 个模型中后者 365 个、前者 340 个，有 25 个只有后者，混用会把 T2 误判成 T1。`supported_parameters` 为空 list 的 3 个模型语义是「未声明」不是「全支持」，必须落 T2/T3。`model.profile` 是 **dict** 不是对象，必须 `prof.get('supports_json_schema_output')`，属性访问会 `AttributeError` 崩在 run 路径上 |

### 2.5 AgentSpec 与表单映射

| # | 修正 |
|---|---|
| **S1** | `instrument` **不是** AgentSpec 字段也不是 `from_spec` 关键字，对应的是名为 `Instrumentation` 的 **capability**。表单不要为它建顶层输入项 |
| **S2** | `AgentSpec.model` 在 spec 层其实是**可选**的（必填只在 `from_spec` 层二选一）。表单若允许留空，`model_validate` **不会**报错，错误推迟成 `UserError` → `agent_spec_invalid` 的 except 必须同时捕 `ValidationError` / `ValueError` / `UserError` |
| **S3** | `json_schema_path` 的 alias 是 **`$schema`** 且未开 `populate_by_name`，写全名会被**静默丢弃**。`spec_json` 入库统一 `model_dump(by_alias=True)` |
| **S4** | `AgentSpec` 是 `extra='ignore'`（未知键静默吞掉），而官方生成的 schema 是 `additionalProperties: false`。所以**写库前必须显式跑一遍** `AgentSpec.model_json_schema_with_capabilities()` 的 jsonschema 校验——决策 2「升级只改 builder 一个文件」这句话要靠这一步才成立，否则上游删字段/改名时旧 spec 静默失效 |
| **S5** | capability 表单字段**绝不能**用 `inspect.signature` 或 `dataclasses.fields` 生成：4 个 capability 覆写了 `from_spec` 且签名不同（`PrefixTools` 的 `__init__` 叫 `wrapped`、spec 里叫 `capability`，照 `__init__` 生成 100% 报错），`dataclasses.fields` 还会把有默认值的参数报成必填并暴露 8 个私有字段。唯一正确来源是 `model_json_schema_with_capabilities()` 的 `$defs['spec_params_<Name>']` |
| **S6** | capability YAML 有 **4 种**合法形状（文档只列 2 种）。表单生成器固定产出最简的两种，但**导入器必须全接受**，否则破坏「AgentSpec 可移植」卖点 |
| **S7** | model 传**字符串**时 `from_spec` 在构造期就解析、强依赖 `OPENROUTER_API_KEY` 环境变量、且 base_url 锁死官网（走不了中转）。必须传 Model 实例。**继续用 `OpenAIChatModel` 而不是 `OpenRouterModel`**——后者对响应缺 `provider` 字段会硬失败，而中转（New API 一类）不保证回传该字段；代价是拿不到上游 prompt-cache 计价优化，已由 P1 把 catalog pricing 提为主价源补偿。这条理由写死在 builder.py 顶部注释里，防止下次升级被人好心改回去 |
| **S8** | `provider.base_url` **不是**装饰性属性：它被真实消费进 `ModelResponse.provider_url` 与 OTel span。走自建 client 时它仍报官网地址——**不影响请求路由与计费，但会污染 trace**，排查中转故障时正好被带偏 |
| **S9** | spec 里的 `MCP` **只能声明 HTTP(S) 地址**，`stdio` 完全无法表达（`from_spec` 强制 `url` 必填、`local` 收窄为 http(s) URL 字符串）。所以决策 1 的「本地 stdio MCP server + 100% 纯净 YAML」不成立：本地 server 必须监听 `127.0.0.1` HTTP，导出的 YAML 会带本机端点，**「100% 纯净可移植」降级表述为「纯净但含本机端点」**。依赖还要补 `pydantic-ai-slim[mcp]` |
| **S10** | pydantic-ai 2.35.3 **没有**任何 OpenAI 兼容端点可复用（`to_openai_responses` / `to_openai` / `to_openai_chat` 全部不存在；`to_web` / `to_cli` 存在，`to_a2a` 已移除）。`/v1/chat/completions` 与 `/v1/models` **全部自建**，无官方实现可抄。省力点只有一个：继承 `pydantic_ai.ui.UIAdapter` 可白拿请求解析与消息 sanitize 框架 |

## 3 契约冻结清单（v0.1 必须定死）

**这一节是本文的核心。** 判据：一旦上线后改动会打断「`base_url` + `sk-xc-` key + `model` 字符串」中任意一环的东西，必须现在定死。

冻结物的形态不是文档而是**代码**：`src/xingcha/contract.py` 里所有正则、闭集、字段清单以常量存在，`tests/test_contract_frozen.py` 是一套黄金测试——**任何改动闭集的提交都会让 CI 变红**。`docs/CONTRACT.md` 由常量生成，不手写。

### 3.1 路径归属

```
对外只有四个前缀：
  /v1/*            OpenAI 兼容面（base_url 就是 https://host/v1）
  /api/v1/*        星槎管理 REST
  /admin/*         Web UI
  /healthz /readyz 免鉴权探针

/v1 下星槎自有路径是一个闭集：
  GET  /v1/models
  GET  /v1/models/{id}          ← 单段；OpenRouter 的 /v1/models/{author}/{slug}/endpoints 按段数区分，留给反代
  POST /v1/chat/completions
  /v1/xc/*                      ← 星槎永久保留区，从不反代
  OPTIONS <任意 /v1 路径>        ← 一律由星槎应答，永不反代

其余 /v1/{path:path} 全部字节级反代到上游（catch-all 最后注册）。
匹配前先归一化：path = re.sub(r'/+', '/', path).rstrip('/')；一律区分大小写。
```

**演进规则**：新增星槎自有端点只能落在 `/v1/xc/*` 下。从反代**收回**任意其它 `/v1` 路径属于破坏性变更，必须 contract 号 +1 并双轨服务。

> **三条是评审在两份草案里都没找到、且上线第一天就存在的坑**：
> - `GET /v1/models/{model}` 是 OpenAI 标准的 retrieve-model，Cherry Studio / Continue 一类客户端会用它验证模型是否存在。不列进白名单就归反代 → 用 Agent slug 去请求会打到 OpenRouter 拿回上游 404，客户端据此判定「这个模型不存在」，而事后拦回来算破坏性变更 → **永久坏掉**。
> - `GET /v1/models/` 带尾斜杠时，FastAPI 的 `redirect_slashes` 在 catch-all 存在时**不生效**，直接匹配 catch-all → 客户端拿到 200、拿到 400 多个上游模型、**一个 Agent 都看不到，且没有任何报错**。
> - 浏览器客户端直连时 CORS 预检由 OpenRouter 的策略决定，而星槎自己的响应头不带 CORS → 表现为「非流式偶尔能用、浏览器直连必挂」。冻结一份（默认空 = 不发 CORS 头）的策略与 `XINGCHA_CORS_ORIGINS` 配置项，后续放开 origin 就是纯加法。

### 3.2 鉴权与 token 格式

```
只认 Authorization: Bearer <token>（scheme 大小写不敏感）。
永不支持 query string 传 key，永不支持 api-key / x-api-key 头。

明文信封（冻结）：sk-xc-<scheme>-<kid>-<secret>
  ^sk-xc-(?P<scheme>[1-9][0-9]{0,2})-(?P<kid>[0-9a-z]{16})-(?P<secret>[A-Za-z0-9_-]{16,86})$

scheme=1 语义：secret = secrets.token_urlsafe(32)（43 字符）
             校验 = 常量时间比较 sha256(secret)
             scheme=1 的总长恰好 68 字符（6+1+1+16+1+43）
```

**为什么切出 `scheme` 与 `kid`**：
- `kid` 是**唯一查表键**，可推导性为零。若像另一份草案那样用「hash 本身」作查表键，将来换成带盐的 argon2id 就无法反查，只能全表逐行 verify，`O(n)` argon2/请求 = 送上门的 DoS——「已签发 key 永不失效」的承诺一到迁移当天就破。
- `kid` 也让**对外显示的前缀不是活体秘密**。用 `prefix = 明文前 14 字符` 的做法会把秘密本体的 8 个字符印在 UI、日志和 `token list` 里。
- `scheme` 是算法分派位。新哈希方案 = 新 scheme 数字，服务端**永久保留全部历史 scheme 的校验分支**（scheme=1 的校验代码标记为「永不删除」），老 key 不重签、不失效。

**库里存**：`scheme` · `kid`（UNIQUE，唯一查表键）· `hash` · `hash_alg TEXT NOT NULL DEFAULT 'sha256'` · `kdf_params TEXT`（JSON，scheme=1 为 NULL，argon2id 的盐与 t/m/p 参数随行走）· `display_prefix`（`sk-xc-1-<kid>`）· `user_id NOT NULL`。**永不存明文**，明文只在签发时打印一次。

**演进规则**：`kid` 长度与字符集不再变化；`secret` 长度可随 scheme 变化（所以信封正则里 secret 段是范围而非定长）。v1 那把 key 就是 token 表里 `user_id=1` 的普通一行，**无任何特例代码**，v2 加多用户不改 token 语义。

**对外错误不做区分**：`token_expired` / `token_disabled` / `invalid_api_key` 一律回 `invalid_api_key`——给公网一个 token 有效性 oracle 是白送的信息。区分只进日志。

### 3.3 model 命名空间与分派（上线后改不了的那一条）

```
按顺序三条，无例外：

① model 以 "xc:" 开头   → 星槎显式命名空间
                          v1 认 xc:agent/<slug> 与 xc:model/<上游 id>
② model 含 "/"          → 上游裸模型 id，原样透传
                          ^[A-Za-z0-9._-]+/[A-Za-z0-9._-]+(:[A-Za-z0-9._-]+)?$
                          （允许 :free / :batch 等变体后缀）
③ 其余                  → Agent slug
                          查不到直接 404 model_not_found，绝不猜测性转发上游

Agent slug 正则（冻结）：^[a-z][a-z0-9]*(-[a-z0-9]+)*$    长度 2–48
  禁含 / : . _ 与大写；保留字 models me health version xc；禁止 xc- 前缀
  slug 是【全局】唯一命名空间：0001 迁移写 slug TEXT NOT NULL UNIQUE
```

**为什么用 `xc:` 而不是 `xc/`**：冒号让显式命名空间在结构上**不可能**与上游的 `vendor/model` 混淆，而 `xc/agent/x` 长得就像一个上游 model id，靠规则顺序才不撞——能靠形状区分就不要靠顺序区分。

**演进规则**：
- 「含 `/` 即上游」这条判据**永不反转**。
- slug 字符集只能**收缩到更严**，不可放宽——放宽会让原本 404 的字符串突然变成有效 Agent。
- slug 发布后**不可改名**：改名写入 `agent_alias`（0001 迁移即建表），旧 slug 永久解析到新 Agent。
- **slug 永远是全局命名空间**。per-user 命名空间只能通过新的显式前缀 `xc:u/<user>/<slug>` 引入，裸 slug 的解析规则**永不因多用户而改变**。
  > 这条是评审找出的雷：两份草案都冻了 slug 正则却都没说唯一性作用域。v2 加多用户时选 per-user 则同一个 `model="extract"` 会随 token 归属解析到不同 Agent（所有既有调用方语义静默改变）；选全局则要事后把 UNIQUE 从 `(owner,slug)` 改成 `(slug)`，在 SQLite 上是建表重灌。
- 验收必须断言 `PRAGMA index_list(agent)` 里 slug 的 unique 索引存在——只断言列存在是不够的。

### 3.4 `GET /v1/models` 的内容、顺序与降级语义

| 项 | 冻结值 |
|---|---|
| 形状 | `{"object":"list","data":[…]}` |
| **顺序** | Agent 行（按 `created_at` 升序）在前，上游行（按 catalog 原序）在后，按 id 去重且 **Agent 优先** |
| Agent 行 | `id=slug` · `object="model"` · `owned_by="xingcha"` · `created=Agent 创建时间戳` · `x_xingcha={kind:"agent", tier, description}` |
| 上游行 | `id=上游原始 id` · `owned_by="openrouter"` · `x_xingcha={kind:"model"}` |
| 过滤 | `?owned_by=xingcha\|openrouter` |
| 是否混入上游 | `XINGCHA_MODELS_INCLUDE_UPSTREAM`，默认 `true` |
| **catalog 拉取失败/过期** | **stale-while-error**：返回上次成功快照，并在 `x_xingcha` 里标 `catalog_stale=true` 与 `fetched_at` |

**顺序必须冻结**，因为部分客户端取 `data[0]` 作默认模型，v2 换排序即静默换模型。
**降级语义必须冻结**，因为客户端会缓存这个列表并把 id 写进会话配置：一次上游抖动如果让接口只返回 Agent 行而不报错，用户配置里的上游模型会被**静默抹掉**；如果返回 502，客户端可能整体判定端点不可用连 Agent 也用不了。

### 3.5 请求字段的三态：honor / ignore / reject

三张闭表，写进 `contract.py`。

| 态 | 含义 | v1 内容（摘要） |
|---|---|---|
| **honor** | 生效 | `model` `messages` `stream` `temperature` `top_p` `max_tokens` `stop` `seed` `presence_penalty` `frequency_penalty` … |
| **ignore** | 接受但**永久无语义** | `user` `store` `metadata` `n`(仅=1) |
| **reject** | 400 `param_unsupported` | `retries` `max_retries` `usage_limits` `response_format` `tools`（Agent 路径）`session_id` |

**元规则（评审补的雷）**：
- **被列入 ignore 的字段永久无语义，永不 honor。** 需要新语义必须用新字段名或走 `x_xingcha` 入参对象。
  > `user` 正是 OpenAI 语义里天然的租户位，v2 做多用户/配额时一定会想拿它当 subject——那一刻所有在 v1 往 `user` 里塞了任意字符串的调用方，行为全部改变。所以**`user` 永久只作日志维度，租户归属永远只来自 token**。
- `session_id` **在 v1 就 reject**，不走「先忽略以后 honor」——同一请求两种语义是无法回退的毁约。将来要支持就叫 `x_xingcha.session_id`，或把 400 放宽成 200（放宽是加法）。
- **reject 表只能缩小，永不把字段从 honor/ignore 移入 reject。**
- `retries` / `max_retries` / `usage_limits` / `response_format` 必须在 reject 表里——实测 `run(retries=)` 与 `run(spec=)` 都能覆盖构造值，不拦住等于让调用方自行放大重试预算、绕过费用护栏。

### 3.6 响应形状

| 项 | 冻结值 |
|---|---|
| **结构化输出的承载** | `message.content` **永远是字符串**：`json.dumps(dict, ensure_ascii=False)`（不缩进；不承诺具体空白）。调用方 `json.loads(content)` 取回 dict。永不改成把 dict 直接放进 content |
| **扩展字段唯一落点** | 所有星槎自有字段只出现在单一顶层键 `x_xingcha` 内，带 `x_xingcha.v=1` 形状版本号。v1 内含 `tier` `cost_usd` `cost_source` `schema_violations` `schema_retries` `run_id` `agent_version`。**响应体除 `x_xingcha` 外不加任何非 OpenAI 键** |
| **金额类型** | `cost_usd` 是**字符串形式的 Decimal 或 null**（不是 number）。`null` 表示无法定价，与真实 0 费用可区分 |
| **usage 的口径** | **整轮累计**，包含全部 schema 重试与工具往返产生的 token 与费用。调用方要折算真实产出成本，用 `x_xingcha.schema_retries` 自行换算。**429 / 422 响应里也带 usage**，否则失败 run 的花费不可见 |
| **SSE 帧序列** | `chunk0 = {delta:{role:"assistant"}}` → 若干 content delta → `{delta:{}, finish_reason:"stop"}` → 可选的 `{choices:[], usage:{...}, x_xingcha:{...}}` 汇总帧 → `data: [DONE]\n\n` |

**usage 口径必须冻结**，因为一次 200 背后可能有 `1+retries` 次模型调用。等你发现「一次调用怎么花了 4 倍」时，最自然的"修正"是只报最后一次尝试——那会让所有基于 usage 的账单核对、配额聚合、成本看板**同时改变口径**，是无法回退的数值毁约。

**演进规则**：`content` 的 str 类型永久冻结（将来要给已解析形式，只能作为 `x_xingcha.parsed` **并行**提供）；`x_xingcha` 内只增字段不递增 `v`，删/改语义必须递增 `v` 并在一个版本内同时提供新旧键；顶层永不新增非 OpenAI 键；帧形状与 `[DONE]` 冻结，把伪流式升级为真 delta（帧数变多）是兼容的。

### 3.7 流式语义

| 场景 | v1 行为 |
|---|---|
| 裸模型直通 | 字节透明转发，上游帧原样出 |
| 纯文本 Agent | **伪流式**：单内容帧 + 结束帧 + `[DONE]`，帧形状与真流式完全一致 |
| 结构化 Agent | `stream=true` 固定 400 `stream_unsupported` |

**为什么纯文本 Agent 在 v1 就发伪流式而不是 400**：虽然 400→200 是加法，但客户端会为此**写死绕过逻辑**（探测到 400 就改走非流式），等真流式上线时反而打断它们。帧形状现在冻结，v0.4 把单帧换成多帧对客户端完全不可见。

### 3.8 错误契约

`type` 为闭集（供 SDK 分支）、`code` 走细粒度，**`type ≠ code`**（另一份草案的 `type == code` 是发出第一个错误响应后就再也回不去的冻结）。

```json
{"error": {"message": str, "type": str, "code": str, "param": null, ...extra}}
```

| type | HTTP | 触发 |
|---|---|---|
| `invalid_api_key` | 401 | 令牌无效 / 禁用 / 过期（对外不区分） |
| `quota_exceeded` | 429 | 附 `subject_type` / `window` |
| `model_not_found` | 404 | slug 不存在或已停用 |
| `param_unsupported` | 400 | reject 表命中，附 `param` |
| `stream_unsupported` | 400 | 结构化 Agent 请求 `stream=true` |
| `request_too_large` | 413 | 超过 `MAX_BODY_BYTES` |
| `schema_violation` | 422 | T2 重试耗尽，附 `retries` 与最后错误 |
| `agent_spec_invalid` | **400** | 用户提交的 spec 不合法 |
| `agent_build_failed` | **500** | spec 无法构造（通常是上游版本变动），需管理员介入 |
| `upstream_error` | 502 | 附 `upstream_status` |
| `upstream_timeout` | 504 | 单次上游请求超时（`ModelAPIError`） |
| `request_timeout` | 504 | 整轮墙钟超时（`asyncio.timeout`） |
| `internal_error` | 500 | 兜底 |

> `agent_spec_invalid` 在草案里是一码两 HTTP，必须拆——用户填错（400）和上游变动（500）是两个完全不同的处置路径。
> 两种超时也必须分开：`Agent.run` **没有** timeout 参数，per-Agent 超时走 `model_settings={'timeout': …}`，整轮墙钟只能靠 `asyncio.timeout`。

**演进规则**：只能新增 `type` 值且必须配一个此前未使用的语义；既有 `type` 的 HTTP 码永不改动、永不改名、永不复用于别的语义；`extra` 字段只加不删。

### 3.9 裸模型直通的透明性与卫生

| 项 | 冻结值 |
|---|---|
| 鉴权 | **直通路径从第一天就强制鉴权**：无有效 `sk-xc-` key 一律 401，绝不透传给上游。这条配一条会红的测试 |
| 请求体 | 缓冲成 `bytes` 后转发（异步迭代器会强制 chunked 被部分中转拒），受 `MAX_BODY_BYTES` 约束 |
| 请求头 | 剥离**全部**客户端 IP 类头再转上游：`X-Forwarded-For` `X-Real-IP` `Forwarded` `CF-Connecting-IP`。否则真实来源交给上游，中转形同白建 |
| 响应头 | **白名单**（不是黑名单）：`content-type` `content-length` `content-encoding` `cache-control` 上游限流头 `x-request-id`。其余全部丢弃——否则上游的 `Set-Cookie` 会落在你自己的域上 |
| 上游 origin | **pin 死**，转发前对 path 归一化并拒绝 `..` / `%2e%2e%2f` / 带 scheme 的绝对路径 |
| 计量 | v1 记 run 行与 token（从上游响应体解析），**不执行配额**。这一点必须写进 RUNBOOK，不能让你误以为 v1 有费用护栏 |

**演进规则**：直通层加配额闸是**收紧**，必须经 `X-Xingcha-Contract` 协商入口发布，不能是一次让调用方突然 429 的毁约。

### 3.10 数据层纪律

**expand → backfill → contract 三段**：一次升级只允许**加**（加列、加表、加索引），删列/改列/改语义拆成**两个**版本发布。理由：你选的升级档位是「重启 + 自动迁移」，新进程跑迁移时旧进程可能还在服务；而 SQLite 的 `ALTER TABLE` 能力有限，事后加 `NOT NULL` / `UNIQUE` 要建新表拷数据，在有真实数据的线上库上就是停机迁移。

**0001 迁移必须一次写对的预留**（事后补＝停机）：
- 所有主体表 `user_id INTEGER NOT NULL REFERENCES user(id)`，seed 一行 `id=1`
- `agent.slug TEXT NOT NULL UNIQUE`
- `token.hash_alg TEXT NOT NULL DEFAULT 'sha256'` · `token.kdf_params TEXT`
- `agent_version.tier TEXT CHECK (tier IN ('T1','T2','T1P','T3'))` —— 四档全列，v1 只实现 T2
- `run_usage.cost_usd TEXT` · `cost_source TEXT`（四态）· `schema_violations INTEGER` · `schema_retries INTEGER` · `extra_json TEXT`
- `agent_alias` 表（slug 改名的唯一出路）

**验收断言到约束级**，不只断言列存在：`PRAGMA table_info` 的 `notnull==1`、`PRAGMA index_list` 的 unique 索引、`cost_usd` 的声明类型是 `TEXT`。
**每个 revision 必须有可用的 `downgrade()`**，且验收要在**线上库副本**上演练：`VACUUM INTO` 出副本 → 跑 `0001→0002` → 逐字段断言此前产生的每一行 run/run_usage 内容不变、新列取默认值 → 再重跑一遍全部 curl 验收。

### 3.11 配置、数据目录与密钥

| 项 | 冻结值 |
|---|---|
| 配置前缀 | `XINGCHA_`，未知 `XINGCHA_*` 变量**启动时 WARN 但不失败** |
| `XINGCHA_HOST` | 默认 **`127.0.0.1`**。默认值变更视为破坏性变更 |
| 数据目录 | `data/xingcha.db`（+`-wal`/`-shm`）· `data/secret.key` · `data/backups/` |
| 权限 | 进程 `umask 0077` · `data/` 0700 · db 与备份 0600 · `secret.key` 0600 |
| 主密钥 | **`data/secret.key` 从第一天就是 MultiFernet 密钥环文件**（每行一把，首行为当前加密 key），用 `Fernet.generate_key()` 生成。**不落 `.env`**（会进 `docker inspect` 与 `/proc/<pid>/environ`）。优先级：**文件 > 环境变量** |
| 启动断言 | 密钥环缺失**而 `setting` 表已有密文** → **拒绝启动**，绝不静默重新生成 |
| 上游 key 来源 | `setting` 表（Fernet）> `XINGCHA_OPENROUTER_API_KEY`（仅首次启动一次性导入 setting 表并 WARN，之后永久忽略） |
| worker 数 | **启动时断言为 1**。进程级 `ConcurrencyLimiter`、内存 flush 缓冲、SQLite 单写者全都依赖它；任何人日后为"提高性能"改成 2，会同时静默打破上游并发封顶、丢一半用量缓冲、并引入 `database is locked`——三个症状互不相关，排查成本极高 |
| WAL | 启动时断言 `PRAGMA journal_mode == 'wal'`，否则**拒绝启动**（bind mount 落在网络盘上必须炸，不能静默降级成零星的 `database is locked`） |

> 不要用 `openssl rand -base64 32` 生成密钥环行——实测 72% 概率产出含 `+` / `/` 的非规范 base64，在逐行解析的密钥环上是隐患。

### 3.12 版本协商

`GET /version`（免鉴权）与 `X-Xingcha-Contract` 请求/响应双向头，响应带 `features` 能力位。

这不是锦上添花：它是唯一能让一次**安全性收紧**（真给直通上配额闸、把某个字段挪进 reject 表）以非硬切方式发布的逃生通道。没有它，将来上闸只能是一次让调用方突然 429 的毁约。

## 4 公网暴露的准入清单（v0.1 的硬门槛）

这台机器挂在公网、后面直连一把付费 OpenRouter key，被打穿等于真金白银流失。下面 10 条是三个镜头评审在两份草案里**都没找到**的，全部必须在 v0.1 上线前落地。前两条属于「上线即可被利用」，不是待办事项。

| # | 风险 | 修正 |
|---|---|---|
| **A1** | **CSRF → 上游 key 被盗**。公网 `/admin/*` 有 cookie 鉴权的 HTML 表单 + 一个能改写「中转 base_url」和 OpenRouter key 的设置页。攻击者只需让你的浏览器 POST 一次把 base_url 指向自己，下一次调用就把付费 key 送上门 | 会话 cookie 强制 `SameSite=Strict` + `Secure` + `HttpOnly`；所有改状态的 admin 请求走 double-submit CSRF token 并校验 `Origin`/`Sec-Fetch-Site`；改设置类操作二次输入密码；`frame-ancestors 'none'` 防点击劫持绕到同一结果 |
| **A2** | **SSRF 兼 key 外带**。设置页那个「测试连接」按钮就是一个带着 OpenRouter key 去打你指定 URL 的 SSRF 原语 | 只允许 `https`（例外仅显式的 `127.0.0.1`）；拒绝 `169.254.0.0/16`（云元数据）、`::1`、`fd00::/8`、默认拒绝全部私有网段；先解析域名再把连接 pin 到该 IP 以挡 DNS rebinding；**测试请求一律用哑 key**，绝不把真实 key 发给尚未保存的 host |
| **A3** | **请求体无上限 = 单请求 OOM**。直通层把 body 整块缓冲成 bytes，Caddy 默认也不限。一个 2GB POST 就打死这个同时承载全部流量、SQLite 写入和内存缓冲的单进程 | Caddyfile 加 `request_body { max_size 10MB }`；应用侧在读 body 前先查 `Content-Length`、对 chunked 做流式累计上限；`MAX_BODY_BYTES`（默认 8MB）**进契约**（事后收紧是破坏性变更）；验收「11MB 请求返回 413」 |
| **A4** | **零速率限制**。不限每 token 速率、不限并发、不限 401 失败、不限登录尝试。直通路径又绕开配额，等于一个不计量不限并发的付费 key 放大器 | 进程内按 token 的令牌桶（请求/分钟 + 在飞并发），**必须同时作用于 Agent 路径与直通路径**；登录失败指数退避 + 锁定；401 交给 fail2ban。**「单 token 并发上限」进契约**，但不要把「永不默认启用」也冻进去 |
| **A5** | **用户 schema 的 ReDoS 打死单进程**。一条 `{"type":"string","pattern":"(a+)+$"}` 由 jsonschema 用 Python `re` 在事件循环上执行，且**每次 schema 重试都跑一遍**，一核打满整个服务停摆 | schema_guard 直接**拒绝 `pattern` / `patternProperties`**，并给整次校验加墙钟上限 |
| **A6** | **远程 `$ref` = 校验期 SSRF**。jsonschema 在未给定封闭 registry 时会真的去取非本地 `$ref`；`{"$ref":"http://attacker/x.json"}` 不是悬空本地引用，探测式 check_refs 拦不住 | 拒绝任何不以 `#/` 开头的 `$ref`；构造 validator 时传入**空的** `referencing.Registry`，让远程取回在结构上不可能发生 |
| **A7** | **错误回显与日志无脱敏**。`UserError`/httpx/openai 的异常文本常带完整 URL、偶尔带 header | 5xx 对外**只给固定文案 + `run_id`**，细节只进日志；日志加正则脱敏 filter（`sk-or-v1-*` / `sk-xc-*`）；转发上游 body/header 前扫掉上游 key；关掉 uvicorn access log 里的 header |
| **A8** | **磁盘打满 = 写失败 + 迁移失败 + 无法启动**，而根因（日志涨满）在监控里完全看不见。compose 默认 json-file 无 `max-size` | compose 配 `logging` 的 `max-size`/`max-file`；`/readyz` 暴露剩余磁盘并在低于阈值时标 `degraded` |
| **A9** | **用量缓冲在重启时静默丢失**。「批量 flush 不在请求路径落盘」+「重启即升级」= 每次升级都静默丢掉内存里那批 run/run_usage 行，**账单数据恰好在你最需要它可信的时刻少报，且丢多少无法事后察觉** | lifespan shutdown 里强制 flush + 落盘；给缓冲设条数与时间双上界 |
| **A10** | **备份不可信**。`cp` 复制活库在 WAL 下**非崩溃一致**；把 db 与密钥环打进同一个 tar 则**密文与密钥同包**，setting 表的 Fernet 加密对「备份泄露」这一最现实的威胁提供零保护 | 用 `VACUUM INTO`（或 sqlite3 backup API）；**密钥独立备份**或备份包再加一层口令；必须做一次「真的删掉 data 再恢复并跑通全部验收」的演练；异地副本 |

另外两条运维层的：`XINGCHA_HOST` 默认 `127.0.0.1` 且 xingcha 容器**不映射任何宿主端口**（只有 Caddy 发布 80/443）；RUNBOOK 必须写明 **Docker 的 `DOCKER-USER` 链会绕过 ufw**——任何人日后为调试加一行 `ports: 8720:8720`，防火墙说 deny 也照样通。

**v1 唯一真正的钱刹车不在星槎里**：v1 不做配额，所以必须在 **OpenRouter 侧为服务端那把上游 key 单独设一个低额信用上限**。这是 v0.1 的**交付物与验收项**，不是风险栏里的一句话。

## 6 「优雅」的可检查定义

不当形容词处理，落成八条机械可查的标准，每个里程碑的验收都过一遍。

| # | 标准 | 怎么查 |
|---|---|---|
| 1 | **单向依赖，无循环**：`api → services → core → db`，`core` 不 import `services`/`api` | 一个 import 方向检查脚本进 CI |
| 2 | **一个概念只有一处定义**：契约字段、错误码、能力清单、命名空间规则各只有一个 source of truth | 全部在 `contract.py`，其余只引用；grep 断言无第二份字面量 |
| 3 | **上游适配点唯一**：pydantic-ai 版本演进的所有兼容处理只写在 `core/builder.py` | grep 断言别处不出现 `AgentSpec` 字段名字面量 |
| 4 | **不发明格式**：Agent 定义就是官方 `AgentSpec` | S4 的官方 schema 校验就是这条的守卫 |
| 5 | **加功能靠加文件，不靠改文件** | 新增档位/能力/模板不改已有模块主干 |
| 6 | **无隐藏状态**：一次调用的生命周期能用一张图讲完；缓存 key 显式 `(agent_id, version)` | 无全局可变单例（`ConcurrencyLimiter` 例外且在 lifespan 里显式创建） |
| 7 | **不留"以后再重构"的临时层** | 宁可少一个功能 |
| 8 | **总代码量小到能整体读完** | 这是"轻量"的唯一硬指标 |

## 7 前端设计方针

**约束先说清**：C1/C3 要求零 Node 构建链、静态资源内嵌进 wheel、离线可用。所以**不引 Tailwind/Bootstrap 的 CDN**——CDN 直接违反离线可用。路线是**手写现代 CSS 设计系统**，这完全能做到美观大气，且总量可控（约 400 行 CSS）。

| 层 | 做法 |
|---|---|
| **设计令牌** | 颜色 / 间距 / 圆角 / 阴影 / 字阶全部走 CSS 自定义属性，定义在裸 `:root`；亮暗双主题（`prefers-color-scheme` + 显式 `data-theme` 覆盖，两个方向都要能赢） |
| **色彩** | 一个中性灰阶 + 一个品牌强调色 + 语义色（成功/警告/危险/信息）。强调色克制使用，只用在主操作与当前态 |
| **字体** | 系统字体栈（`-apple-system, "Segoe UI", "PingFang SC", "Noto Sans CJK SC", sans-serif`），数字与 token/JSON 用等宽栈。中文字重不要用 300 以下 |
| **排版** | 8px 基准栅格；内容区最大宽度约束；表格是这个后台的主体，行高与列对齐（金额右对齐、等宽）比装饰重要 |
| **交互** | HTMX 局部刷新；每个异步操作有明确的 loading 与错误态；动效只用 `transform`/`opacity`，时长 ≤ 200ms |
| **信息密度** | 后台不是落地页：优先可扫读的密度，而不是大留白。关键数字（今日调用/费用/错误率）用一行 stat 卡，其余进表格 |
| **可达性** | 焦点环不许移除；对比度 ≥ 4.5:1；表单每个输入有 `<label>`；危险操作二次确认 |
| **页面清单** | v0.1：登录 · 总览 · 密钥 · 调用记录 · 设置。v0.2 追加：Agent 列表 · Agent 编辑（含 schema 字段编辑器与 lint 提示）· 用量 |

**"大气"的具体落点**：克制的配色 + 稳定的栅格 + 一致的圆角与阴影层级 + 不炫技的动效。不靠渐变和大字号堆砌。

## 8 部署与运维（照 `finance-data-crawler/deploy/` 的形状）

**形态收敛成一种**：`docker compose`（xingcha + caddy）。理由——VPS 已有 docker；`compose up -d` 正好就是你已接受的 1–2 秒中断；Caddy 三行拿到自动 TLS；xingcha 容器**不映射任何宿主端口**，只有 Caddy 发布 80/443；应用除 SQLite 外无状态，所以不堵死日后加蓝绿。

> 不同时交付 systemd + Dockerfile + compose 三种。三种并列等于把三套运维范式一起变成事实上的接口（你的 unit 文件和 compose 文件都会被长期保留），日后砍掉任一种都是毁约。`Dockerfile` 只作为 compose 的构建输入，不单独承诺。

**`deploy/deploy.sh` 照 fin 的骨架**：前置依赖检查（缺失时给可直接执行的安装命令，不只报错）→ 幂等 clone-or-update（更新时 `git reset --hard origin/<branch>`，部署机以远程为准）→ 首次从 `.env.example` 生成 `.env` 后**主动 exit 并提示填哪几项** → `--no-run` 把「更新」与「启动」解耦 → 脚本注释写**为什么**，尤其是坑。

**`deploy/README.md` 照 fin 的章节结构**：前置依赖表 → 编号生产步骤 → 环境特定警告 → 更新流程 → 开机自启与崩溃重启 → 脚本参数 → 安全注意。

上线序列里有三个**顺序**约束（做错会卡在最后一步）：
1. 先做 DNS A 记录并确认生效
2. **再** `docker compose down` 掉 Dify，腾出 80/443
3. Caddy 先用 **staging CA** 走通一遍再切正式 CA，避免撞 Let's Encrypt 速率限制
4. `caddy_data` 用命名卷持久化证书，重启不重签
5. 镜像用 `docker save | zstd` 传上去，VPS 不装构建链

`stop_grace_period: 30s`。**如实声明**：升级时正在跑的长请求会被切断——这是你选的升级档位（决定 4）接受的代价。

**fin 那条「Caddy 反代致命坑」被抄错了跳数**，必须纠正：`header_up -X-Forwarded-For` 抹除 XFF 是给 **Caddy 当 OpenRouter 中转**那一跳用的；**客户端 → 星槎**这一跳恰恰**需要** XFF/X-Real-IP 才能记录真实来源 IP。抹除客户端 XFF 的职责在 `passthrough.py` 转发给上游时执行（3.9）。
